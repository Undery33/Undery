## 이름으로 정보를 찾는 서비스

DNS(Domain Name System)는 도메인 이름으로 자원 레코드를 찾는 분산 시스템입니다. A 레코드는 IPv4 주소를, AAAA 레코드는 IPv6 주소를 나타냅니다. 이름을 주소로 찾는 작업과 그 주소의 서비스에 접속하는 작업은 별개입니다. DNS 응답을 받았다고 웹 서버까지 정상이라는 뜻은 아닙니다.

서버 운영에서는 **재귀 리졸버**와 **권한 서버**를 구분합니다. 재귀 리졸버는 클라이언트 대신 답을 찾아 캐시합니다. 권한 서버는 자신이 담당하는 영역인 존(zone)의 레코드를 관리하고 답합니다. 하나의 서버 제품으로 두 역할을 구성할 수 있어도 역할과 접근 정책은 따로 이해해야 합니다.

## 위임을 따라가는 질의

캐시가 없는 리졸버가 `example.com`을 찾는 예시를 보겠습니다. 루트 서버는 `.com` 네임서버를 안내합니다. `.com` 서버는 `example.com`의 권한 네임서버를 안내합니다. 이 두 응답은 다음 서버를 가리키는 **위임**(referral)입니다. 리졸버는 마지막 권한 서버에서 A 레코드를 받아 클라이언트에 전달합니다.

모든 조회가 이 경로를 처음부터 거치는 것은 아닙니다. 리졸버는 캐시한 레코드나 위임 정보를 재사용할 수 있습니다. 아래 모형은 역할을 분명히 보기 위해 A 레코드의 캐시에 집중합니다.

## 캐시와 TTL을 직접 확인하기

`질의 시작`과 `다음 단계`를 눌러 첫 응답까지 진행합니다. 곧바로 다시 질의하면 캐시 HIT로 짧아집니다. 이어서 `원본 레코드 변경`을 눌러도 캐시의 남은 TTL 동안은 이전 주소를 응답합니다. `30초 경과`를 두 번 눌러 TTL을 만료시킨 뒤 다시 질의하면 새 주소를 가져옵니다. 캐시를 읽는 것만으로 TTL이 새로 시작되지는 않습니다.

## 운영 시 확인할 사항

- 레코드를 관리하는 권한 존과 상위 영역의 NS 위임이 일치하는지 확인합니다.
- 변경이 늦게 보이면 질의한 리졸버와 남은 TTL을 확인합니다. 캐시는 서버마다 다를 수 있습니다.
- 재귀 질의를 허용할 클라이언트 범위와 DNS의 UDP·TCP 53번 통신 경로를 확인합니다.

실습의 `example.com` 응답은 설정한 예제 데이터입니다. 실제 도메인을 조회하지 않으며 `203.0.113.0/24`는 문서용 주소 범위입니다. 실제 환경의 CNAME, DNSSEC, 오류 응답과 만료 캐시의 예외 처리 정책은 별도로 다뤄야 합니다.
