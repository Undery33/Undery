# 생일 메시지 관리

`https://undery.link/birthday/memo/admin`에서 기존 GitHub 관리자가 큰 벽의 메시지를 작성·조회·검색·수정하고 숨김/공개, 휴지통 이동/복구를 수행합니다. 공개 방문자에게 웹 작성 권한을 추가하지 않습니다. 월드의 입력·생성·URL 복사/붙여넣기 등록은 그대로 유지합니다.

월드 작성란의 닉네임 행은 숨겨져 있으며 접속한 VRChat 표시 이름을 자동으로 사용합니다. 서버는 URL로 전달된 닉네임을 받으므로 이 표시 이름 자체는 VRChat 계정 소유권 검증 수단이 아닙니다. 관리자 권한은 이 이름과 무관하게 기존 GitHub 소유자 인증으로만 부여합니다.

## 사용 흐름

1. 기존 관리자 GitHub 계정으로 로그인합니다. `/admin`도 메시지 관리 화면으로 연결됩니다.
2. 새 메시지의 닉네임과 내용을 입력합니다. 바로 공개하거나 숨김 상태로 보관할 수 있습니다. 닉네임은 필수이며 공백·보이지 않는 문자만 입력할 수 없습니다.
3. 목록에서 닉네임 또는 내용으로 검색하고 공개/숨김/휴지통별로 확인합니다.
4. 수정은 내용을 저장하며, 숨기기는 공개 목록과 월드 표시에서 제외합니다.
5. 휴지통 이동은 해당 메시지를 선택하고 확인란을 체크한 뒤 다시 확인 버튼을 눌러야 합니다. 영구 삭제 기능은 없습니다.
6. 휴지통 복구는 숨김 상태로 돌아갑니다. 내용 확인 후 공개하기를 누릅니다.

관리자 변경은 서버에 즉시 반영되며 현재 월드에는 다음 조회 때 반영됩니다. 별도 창에서 같은 메시지를 먼저 바꿨다면 기존 버전의 저장은 HTTP 409로 거부합니다. 입력 내용과 서버의 최신 내용을 나란히 확인한 뒤, 명시적인 재저장 버튼으로 최신 버전에 작성 중인 내용을 반영할 수 있습니다. 편집 중에는 다른 항목이나 필터가 입력 내용을 덮어쓰지 않습니다.

방문자가 등록 때 받은 [비밀 코드로 본인 메시지를 삭제](birthday-memo-owner-deletion.md)해도 같은 `deleted` 휴지통 목록에 보관됩니다. 원문·등록시간은 유지되고 관리자는 기존 복구/공개 흐름을 그대로 사용합니다. 방문자 변경은 별도의 `owner_events`에 기록하며 GitHub 관리자 행위로 기록하지 않습니다. 관리자 복구 후 예전 삭제 URL을 재시도해도 다시 삭제되지 않습니다. 비밀 코드 보유자가 새 삭제 요청을 만들면 의도적인 새 휴지통 이동은 가능합니다.

## 인증과 요청

기존 OAuth·소유자 ID·쿠키·CSRF 계약은 [관리자 인증 문서](admin-auth.md)를 따릅니다. 관리 목록의 모든 GET도 서버 세션 검증을 거치며, POST에는 세션과 정확한 Origin, `X-CSRF-Token`이 필요합니다. 소유자 ID를 본문에서 받지 않습니다. 관리 경로는 no-store/noindex/no-referrer를 사용합니다.

`GET /birthday/memo/admin/entries?page=0&status=all&q=...`은 페이지당 50개를 최신순으로 반환합니다. `status`는 `all`, `visible`, `hidden`, `deleted`이며 검색은 닉네임/본문의 문자 그대로 포함 여부입니다. `%`, `_`를 검색 와일드카드로 해석하지 않습니다. `entries`의 각 항목은 공개 필드에 `status`, `version`(10진수 문자열), `updatedAt`을 추가합니다.

`POST /birthday/memo/admin/entries`는 16 KiB 이하 JSON만 받으며 본문 읽기 제한은 10초입니다.

| action | 필드 | 동작 |
| --- | --- | --- |
| `create` | requestId(UUID v4), nickname, message, status=`visible` 또는 `hidden` | 관리자 메시지 추가 |
| `update` | id, version, nickname, message | 같은 ID의 표시 내용 수정 |
| `hide` / `show` | id, version | 공개/숨김 변경 |
| `trash` | id, version | 데이터 보존, 휴지통으로 이동 |
| `restore` | id, version | 휴지통에서 숨김 상태로 복구 |

알 수 없는 필드·행위, 잘못된 ID/버전, 허용되지 않는 상태 전환을 거부합니다. 모든 변경은 게시판 잠금·행 잠금·버전 검사를 거친 트랜잭션입니다. 관리 이력에는 메시지 ID, 행위, 관리자 숫자 ID, 버전, 시간만 기록하며 내용이나 자격 증명을 복제하지 않습니다.

신규 작성의 요청 UUID는 같은 입력의 재시도 동안 유지합니다. `management_requests`는 요청 UUID·관리자·입력 해시·원래 작성 영수증을 저장하여 DB 저장 후 응답만 끊겨도 같은 요청이 중복 메시지를 만들지 않게 합니다. 같은 UUID로 다른 내용을 제출하면 409로 거부합니다. 이 영수증과 방문자 URL 영수증은 복구 가능한 삭제 정책과 함께 보존하며 공개 API로 관리 영수증을 노출하지 않습니다.

## 공개 피드와 원본 영수증

공개 feed는 `visible` 항목만 표시합니다. 기존 `revision`·페이지 크기 150·오래된 순서 계약을 유지하고 모든 페이지에 `moderationRevision`을 추가합니다. 값은 PostgreSQL bigint의 선행 0 없는 10진수 문자열이며 초기값은 `"0"`입니다. 관리자 변경 또는 본인 메시지 휴지통 이동이 실제로 발생할 때만 증가합니다. 일반 월드 등록은 증가시키지 않습니다.

Unity는 새로운 moderationRevision을 읽으면 표시 캐시를 다시 구성하여 같은 ID의 수정·숨김·복구를 반영해야 합니다. 오래된 revision 응답이 뒤늦게 도착하면 무시합니다. 현재 totalPages보다 큰 기존 페이지도 HTTP 200과 빈 entries, 현재 revision을 반환하므로 숨김 후 사라진 마지막 페이지에서 새로 조회를 시작할 수 있습니다.

토큰의 `receipt`는 원래 업로드한 닉네임·내용·생성시간을 고정 저장합니다. 관리자 수정은 공개 `entries`만 바꾸며, 같은 등록 URL의 재전송은 기존 원본 영수증을 반환합니다. 재전송으로 수정 내용을 되돌리거나 숨김/휴지통 메시지를 다시 공개하지 않습니다. 기존에 소비된 토큰은 마이그레이션 때 현재 원본 내용으로 백필합니다.

## 적용·복구

1. 기존 실제 DB 이름·역할과 현재 스키마를 확인하고, 보호된 전체 백업 또는 메모 스키마 백업을 생성하여 `pg_restore --list`와 전체 디코딩으로 확인합니다. 운영 연결 문자열·비밀번호는 출력하지 않습니다.
2. `src/lib/birthday-memo-management-migration.sql`을 기존 DB에 명시적으로 적용합니다. v1 메모 마이그레이션이 먼저 적용되어 있어야 합니다. HTTP 요청으로 자동 적용하지 않습니다.
3. 이 변경은 `birthday_memo`에 상태/버전/수정시간/원본 영수증 열, 게시판 변경번호·관리 이력·관리 작성 영수증 표만 추가합니다. 기존 public 데이터·인증 표의 구조를 바꾸거나 메시지를 삭제하지 않습니다. 기존 메시지에는 공개 상태를 부여하며 적용 전후 공개 행수와 ID 지문을 비교합니다. 앱 역할이 소유자가 아니라면 해당 추가 표/sequence와 entries UPDATE 권한만 검토하여 부여합니다.
4. 기존 OAuth 설정 네 키를 서버의 보호된 설정에서 재사용하고, 프록시가 지정한 POST 경로만 허용하도록 구성합니다. callback code/state 및 Cookie가 로그에 기록되지 않게 합니다.
5. 배포 전후 공개 feed, 익명 관리 API 거부, 실제 관리자 로그인과 테스트 전용 메시지 작업을 확인합니다.

롤백할 때 추가 열/표를 삭제하지 않습니다. 관리 변경 전 v1 앱은 상태를 해석하지 않아 숨김/휴지통 메시지를 다시 표시할 수 있으므로, v1 이미지로 돌아가야 한다면 공개 메모 기능을 먼저 중단하고 상태를 이해하는 빌드로 복구해야 합니다. 운영 메시지의 상태·내용을 자동으로 되돌리거나 데이터를 지우지 않습니다.

## 검증 범위

입력·권한·CSRF·오류 응답 단위 검사와 실제 PostgreSQL 검사로 원본 영수증, 검색, 숨김/복구, 버전 충돌, 변경번호, 빈 후속 페이지를 확인합니다. PostgreSQL 검사는 기존 `undery_test`의 무작위 전용 스키마만 만들고 제거하며 기존 표를 건드리지 않습니다.

GUI는 실제 앱에 별도의 테스트 DB·세션 fixture를 연결하여 확인할 수 있습니다. 운영 세션이나 운영 메시지를 임의 생성하지 않습니다. 로그인 공급자의 실제 승인, 실제 VRChat 여러 인스턴스, 서버 재시작 유지 확인은 각각 별도 검증 항목입니다.
